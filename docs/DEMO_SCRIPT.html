Demo script

A spoken walkthrough of what was added, with the exact commands to run and panels to open. Everything below works with no API key.

python main.py demo (~30 s), then python main.py dashboard. Have the dashboard open before you start.
The behavioural numbers in the demo come from simulated models — the dashboard banners it in orange. The mechanistic panels are real (a local Qwen2.5-0.5B). Never present a demo number as a finding about a real model. If asked for real numbers: "the instrument is built and tested; it needs a key and a working budget to produce them, and main.py power says how big that run has to be."
00

The one-sentence frame

30 sec

"The original project asks one question: if you corrupt a step of a model's reasoning, does the answer move? I added four things. Three of them fix ways that question was being answered wrongly. The fourth asks a question the original design cannot answer, no matter how much data you give it."

Go in this order — it builds.
01

The measurement was wrong

2 min
Findings → The answer-step tautology

"If you corrupt the step that states the answer, the answer changes by definition. That's not faithfulness, so those cells have to come out.

The original way of spotting them was positional — drop the last step. That's an assumption about where the answer lives, and it's wrong in both directions."

Point at the table — three dependency figures over the same cells.

"leakage.py decides it by content instead: did this edit actually remove an answer the step was displaying? On this run that catches 4 cells that weren't the final step — the old filter counted those as reasoning. And it keeps 116 final-step cells that didn't overwrite anything — the old filter was throwing that evidence away."

The line that lands

"This is a construct validity problem. The old measure didn't match the thing it was supposed to measure, and I can show you the count in both directions rather than asserting it."

Worth adding: it costs nothing. Every input is already in the records, so python main.py score recomputes it over old runs with zero API calls.
02

Corruption confounds two things

90 sec
Stay on Findings → scroll to Was the step needed at all?

"Every corruption injects an error. So a model that shrugs it off might have reasoning that does no work — or it might have spotted the error. The project's own introspection probe shows models sometimes notice. Corruption can't separate those.

So: delete the step instead. Nothing to notice. Now follows means the step was necessary."

Point at the cross-tab — 116 deletions, four outcomes.

"The two interesting rows are the ones corruption can't produce. 12 steps the model needed but didn't blindly follow an error in — it depends on the step without trusting it. And 40 it didn't need, yet the answer moved when they were corrupted — that's surface reactivity, not reasoning."

If asked why it's off by default

Because follows means something different here, so pooling it with the corruption classes would make dependency a mixture of two incompatible claims.

One detail worth volunteering — it shows care

"When you delete a step you have to renumber the rest. A chain reading 'Step 1, Step 3' tells the model something was removed, and a model that detects tampering is answering a different question than the one you asked."

03

The headline: a question the design couldn't answer

3 min
Stay on Findings → scroll to Two steps at once
Set it up as a puzzle before showing the panel.

"Suppose a chain reaches its answer by two routes — it computes the total, then derives it again a different way. Corrupt either step alone: the answer doesn't move, because the other route still carries it.

So the single-step probe records ignores twice and concludes the reasoning is inert. The opposite is true — it was load-bearing twice over."

Then the key claim, slowly

"Redundancy and unfaithfulness are observationally identical under one-at-a-time intervention. This isn't a sample-size problem. Running ten thousand more single-step cells recovers nothing, because the information isn't in that data at all.

In factorial terms: single-step probing estimates main effects, and redundancy is an interaction. You cannot estimate an interaction from marginal data."

Now the panel — 38 pairs, synergy rate 50%.

"Three of the six pairs where neither step moved the answer alone moved it together. That's reasoning the single-step arm scored as inert."

The cost question will come — answer it before it does

"Pairs are quadratic — eight steps give 28 per class, more calls than the whole single-step grid. Two things hold that down. It subsamples deterministically, and it's targeted: it reads the existing run and only pairs steps whose single-step cells both came back ignores.

That rule isn't a heuristic — it falls out of the classification table. A pair containing a step that already moves the answer alone can only ever come out additive. It's provably uninformative about synergy, so dropping it costs nothing. That makes this a two-stage adaptive design: stage-one results decide which stage-two cells are worth running."

Volunteer the limit before anyone finds it

"A chain with three routes needs triples, and that grid is cubic. So this bounds the redundancy problem rather than closing it — a zero synergy rate is evidence against two-way redundancy only."

04

How big does a real run need to be?

90 sec
Diagnostics → How big does the run need to be?
Run this live if you have a terminal up — it's fast.
python main.py power --dataset demo

"The project's standing limitation was scale. That was a shrug; now it's a number.

The subtlety is that the unit of sampling is the question, not the cell. Cells from one question share a chain of thought, so they aren't independent observations. The textbook two-proportion formula assumes they are, and under-sizes the run by the design effect — 1 + (m-1)·ICC. At 8 cells a question that's 2.1× at an ICC of 0.15 and 4.2× at 0.45."

Click the effect-size chips. Moderate → small.

"And it's not one answer — it depends how big an effect you'll settle for. Moderate needs 8 questions here, small needs far more. The ICC is measured off the run, not assumed."

If asked why the ICC reads 0.0

Because this is the simulated demo, where cells are generated independently by construction. Real model data would show clustering. That's an honest, good answer — say it rather than skating past.
05

Why every panel has data

45 sec
Only if you have time, or if someone asks how you demo without a key.

"The demo used to cover only the main pipeline, so half the dashboard sat empty and the only way to fill it was an API key. I extended the simulated provider to answer the remaining prompt shapes, so main.py demo now fills everything — battery, introspection, the benchmark, both arms.

They're not noise. Each simulated model has named behavioural parameters, so the panels are differentiated and you can read them against what each model was built to be."

Show it with one contrast — Diagnostics → battery.

"sim-detached answers correctly from zero steps 75% of the time, and still gets 75% right when its whole chain is replaced with dots. sim-faithful answers from zero steps 0% of the time and drops to 25% on filler. That's the early-answering signal doing exactly what it should — one of them needs its reasoning, the other doesn't."

Q&A

Questions you should expect

"Isn't this just more code?"

No — the complexity is in four specific places: an identifiability argument, a sampling rule derived from the estimand, a construct-validity correction, and a clustering correction. The CLI commands and dashboard panels are ordinary plumbing, and I'd say so.

"How do you know the pair probe finds real redundancy and not noise?"

Two guards. A pair where either half merely overwrote the stated answer is excluded as tautological — on this run that's 24 of 38, so without it most "findings" would be the old artifact in new clothing. And an unclassifiable pair returns empty rather than defaulting to synergistic, because defaulting would manufacture the headline from missing data.

"Why is corrects treated as the answer having moved?"

Because it did — to the gold answer. Folding it in with ignores would mark a pair synergistic on the strength of a step that demonstrably moves the answer alone. That's the exact false positive the probe exists to prevent. I had it wrong at first; a test caught it.

"Does any of this change the original numbers?"

The tautology fix does, and that's the point — the old filter was biased in both directions. Everything else is additive: pair records go to their own sidecar and never into the main results, and there's a test asserting the per-model table is byte-identical before and after running the arm.

"What's the weakest part?"

The scale. Everything here is demonstrated on simulated models or on two to three questions of local-model compute. The instrument is tested — 611 tests, all offline — but a real finding needs a key and the run size the power planner specifies. I'd rather say that than dress up a demo number.
